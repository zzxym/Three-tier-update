# 软件命名与架构

## 三角色命名

| 角色 | 名称 | 词根含义 | 部署位置 | 职责 |
|------|------|----------|----------|------|
| 中心源 | **Propel** | pro- 向前（forward） | 中心服务器 | 版本总源，向前推送版本 |
| 内网缓存节点 | **Repel** | re- 回拉（back） | 内网 / 分支机构 | 从中心源把版本回拉，作为内网中继节点分发 |
| 终端客户端 Agent | **Impel** | im- 向内（into） | 内机终端 | 在内机驱动、执行更新 |

词根方向对应三种动作：**pro** 推送 / **re** 回拉中继 / **im** 向内执行。

## 当前工程映射

- **Propel（中心源）**
  - `PropelService`（原 OriginService）→ `PropelService.exe`：中心源 HTTP 文件服务（扁平 token 鉴权 + 块级分发），可当 Windows 服务运行。
  - `PropelControl`（原 ServerConfig）→ `PropelControl.exe`：Propel 服务的图形管理前端（配置 / 前台启动 / 生成 start.bat / 安装·启停·卸载服务）。
  - `ManifestGen` → `MakeManifest.exe`：manifest.json 生成工具（逐文件 sha256 + 大文件 2MB 块哈希）。
  - 配置文件：`propel.json`（由 PropelControl 写入、PropelService 读取）；日志：`propel.log`；Windows 服务名：`Propel`，显示名：`Propel 服务`。
- **Repel（内网缓存节点）**
  - `RepelService`（原 Repel）→ `RepelService.exe`（核心服务）：内网缓存中继节点。P2P 协调（peer register/query）+ 本地缓存兜底；未命中时从上游 `Source`（即 Propel 中心源）回源取数并落盘缓存。可直接运行（前台）或作为 Windows 服务运行（服务名 `Repel`）。
  - `RepelControl.exe`（图形管理前端，镜像 PropelControl）：配置 / 前台启动 / 生成 start.bat，以及安装、启停、卸载 `Repel` 服务；配置写入同目录 `repel.json`。
  - 启动参数（RepelService.exe）：`--port`（默认 80）、`--source <Propel 地址>`、`--tokens`、`--cache`（默认 `repel_cache`）；配置文件 `repel.json` 可省去命令行参数。修改 `repel.json`（tokens/source/cache）会被服务自动热更新、无需重启（`port` 变更仍需重启；PropelService 同样支持 `propel.json` 热更新）。
  - 注意：使用 `HttpListener` 监听低位端口（如 80）需管理员或 `netsh http add urlacl`；回源时透传客户端 token。
- **Impel（终端客户端 Agent）**
  - 终端 Agent，负责在内机驱动、执行更新。**当前实现 = 现有 `WpfDock`（AssemblyName `MenuClient`）中的更新子系统**，核心能力已具备（详见下方“Impel 规划”）。

## 同步源优先级（终端侧）

客户端拉取顺序：`peers（同级已更新终端）→ Repel（内网缓存节点）→ Propel（中心源）`，缺失时逐级降级。

## Impel 规划（终端 Agent）

Impel 即部署在内机的“更新 Agent”，把中心源/缓存节点的版本驱动、落地到本机应用。现有 `WpfDock/Services/Update/` 已是实现蓝本，规划如下：

### 1. 现有能力（可直接复用）
- `UpdateEngine`：后台定时检查 + 混合同步（peers → Repel → Propel）+ 原子切换（App ⇄ App.staging ⇄ App.old）+ 失败开放（任何源不可用保留本地运行）。
- `PeerProvider`：局域网 HttpListener，仅暴露「已校验通过」的文件（白名单 + 实际 sha256 校验），支持 `?off=&len=` 块级。
- `PeerDownloader`：多源下载器；≤32MB 整文件拉取，>32MB 按 2MB 块从多源拉取、逐块 sha256 校验、断点续传。
- `PeerDiscovery`：借助 Repel 协调器做 register/query（上报已 latest 且已校验的 hash 集合 + providerUrl）。
- `Manifest`：manifest 模型、sha256、块构建、Diff（本地 vs 远程，并校验本地实际哈希防损坏）。

### 2. 命名与术语对齐（更名时一并做）
- 工程 `WpfDock`（AssemblyName `MenuClient`）→ `Impel`；命名空间、产物名同步。
- 源码注释/变量中的概念术语对齐：`branch` → `Repel`、`origin`/`servers` → `Propel`/`servers`；配置项 `cfg.Branch` → `cfg.Repel`、`cfg.Servers` → `cfg.Propel`（或统一为 `Sources` 列表保留多中心源）。
- `Manifest` 的 JSON 键（app/version/files/path/size/sha256/blocks/off/len）保持不变，已与 Propel 对齐。

### 3. 部署形态建议
- 现状为 WPF WinExe（带 UI 的停靠栏/启动器）。作为“Agent”，建议：
  - 系统托盘常驻 + 开机自启；提供“静默更新模式”（无 UI 仅后台同步）。
  - 或将 `UpdateEngine` 抽成独立后台进程/Windows 服务 `ImpelAgent`，UI 仅做管理与可视化，避免更新被 UI 会话生命周期影响。

### 4. 配置契约
- 字段：token、apps 列表（id / 本地 root / 进程名）、Repel（host/port）、Propel（servers 地址列表）、更新间隔、Peer 共享开关与端口。
- 与 Propel/Repel 的接口契约：manifest.json 协议、扁平 token 鉴权、`?off=&len=` 块级请求、`/peer/register`、`/peer/query` 协调接口，均已对齐。

### 5. 下一步
1. 将 `WpfDock` 工程更名为 `Impel`（产品名与术语对齐）；
2. 拆分/强化 Agent 形态（托盘常驻 + 静默模式 or 独立 `ImpelAgent` 服务）；
3. 端到端联调：Propel → Repel → Impel 三级同步、块级续传、失败开放。

> 注：`WpfDock`（即未来 Impel）现有代码中仍用 `branch`/`origin` 等概念术语，将在 Impel 更名时统一对齐为 Repel/Propel；框架枚举 `SeekOrigin` 不受影响。
